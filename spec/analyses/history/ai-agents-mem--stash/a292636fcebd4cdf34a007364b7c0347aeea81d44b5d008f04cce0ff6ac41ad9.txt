## Change review - 2026-10-28

**Background claims prevent some duplicate jobs, while embedding writes have uneven stale-result guards.** Reviewed commit `40c70217107472f6e6c5c15e9481ab9dd41096f1` (commit date `2026-10-27T17:03:05Z`). Compared with `cfb7051ded81e3cef9323250a98793ddef191031`; the complete Git comparison contains 784 changed paths.

Embedding reconciliation selects batches of 32, clips text and clears empty embeddings to avoid poisoning a provider batch. Page updates compare original full content and deletion state before clearing stale, but table/history/trace/file/source-table writes use only row IDs after asynchronous embedding. Those paths can overwrite a newer invalidation with an old vector. All selected paths zip returned vectors with rows without asserting exact cardinality, and reported refreshed counts describe selected IDs rather than confirmed affected rows. Overlapping reconciliation workers are not claimed/locked in this module.

Reward-model and scoring tasks use queued-to-running UPDATE RETURNING claims before dispatch, preventing ordinary duplicate broker delivery from restarting those jobs. Remote dispatch is separated from metadata persistence so a failed write does not falsely mark a submitted job failed. That leaves a recovery obligation if dispatch succeeds but its remote ID is not durably saved. The generic tracked helper is unconditional and GEPA calls it directly, so the claim discipline is not universal here. The UI maps finite [0,1] checkpoints, preserves null estimates and labels interpolation between observations; its smooth curve remains a display estimate, not a verified task-completion signal.
