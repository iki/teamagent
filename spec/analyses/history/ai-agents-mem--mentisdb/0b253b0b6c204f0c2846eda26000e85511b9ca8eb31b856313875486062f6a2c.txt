# mentisdb

Typed append-only memory records with hash chaining, explicit relations and derived-index synchronization.

Source: [mentisdb](https://github.com/CloudLLM-ai/mentisdb) · Snapshot: `4c9b95041da68c5a26dece9f8776ff54b05b910c` · Category: `ai-agents-mem`.

Appending validates references and translates referenced indices into typed relations with validity timestamps. Optional deduplication compares normalized token sets against a bounded recent window using Jaccard similarity; a sufficient match adds a Supersedes relation. The record includes agent identity, confidence, importance, source episode and the previous record hash. The implementation computes a new hash, writes the record to durable storage, updates in-memory lexical/query indexes, records invalidating relations, and synchronizes vector sidecars and registries.

## Harness implications

The key reusable idea is durable evidence before derived views. Store human inputs, observable tool events and public agent conclusions as attributed records, then build searchable projections. A correction should append an explicit relationship to the earlier claim rather than erase the history. Hash chaining can detect some tampering when a trusted checkpoint exists, but it does not establish that an agent's assertion is true. Do not interpret the project's term thought as permission to retain hidden model chain-of-thought.

## Limitations and tradeoffs

Jaccard similarity is lexical similarity, not proof of semantic equivalence or supersession; near-identical statements can disagree through negation or a changed number. Automatically marking such a record superseded could hide useful evidence. Storage succeeds before several derived-index operations that may fail, so callers need reconciliation and idempotency semantics rather than assuming a returned error means nothing was written. An in-memory chain and sidecars need workload-specific scale testing.

## Adoption and validation

Borrow the event-log and correction-relationship design; evaluate the database as an optional local implementation. Disable automatic supersession until validated on the actual corpus. Test crash after durable append, duplicate client retries, invalid references, sidecar failure, replay integrity, contradictory near-duplicates and tenant separation. Keep deletion/redaction policy explicit because append-only auditability and erasure requirements need deliberate reconciliation.

**Signed memory records need explicit policy and bootstrap trust.** The new [access-policy module](https://github.com/CloudLLM-ai/mentisdb/blob/67cb559d3b004951232387ea694df4c490d12ba1/src/access.rs) defines Open, Signed and Allowlist modes; chains without valid policy records begin Open. Governance records require canonical JSON, a bounded key count of 1,024, unique key identities, a sorted key-set commitment, sequential policy numbers and the exact previous policy-record hash. The genesis signer must belong to its own proposed key set; later changes require a current governor. That authenticates possession of the selected key, not the external authority of the first governor. Replay records invalid governance entries and skips them, leaving the last valid policy in force; an absent valid genesis therefore remains an explicit trust decision, not automatic restrictive access.

The inspected [signing primitives and payload construction](https://github.com/CloudLLM-ai/mentisdb/blob/67cb559d3b004951232387ea694df4c490d12ba1/src/signing.rs#L180-L599) reject malformed or weak public keys and call strict Ed25519 verification. Version 2 domain-separates thought signatures and binds chain identity, author, previous chain hash and encoded semantic fields. Separate registration proofs bind chain/agent/key/public-key/timestamp. The encoder normalizes tags, concepts and scores before signing, so a signature authenticates the agreed normalized representation. It does not establish factual truth, retrieval relevance, execution authorization or the identity of a human operator.

The complete added [access-policy fixtures](https://github.com/CloudLLM-ai/mentisdb/blob/67cb559d3b004951232387ea694df4c490d12ba1/tests/access_policy_tests.rs) exercise wrong signatures, cross-chain/position replay, revocation with historical verification, unchanged signed relations, legacy v1 acceptance on Open chains, v2 requirements in Signed mode, allowlisted keys, governor transitions, stale-head rejection, reopening and invalid-record replay. The complete added [signing fixtures](https://github.com/CloudLLM-ai/mentisdb/blob/67cb559d3b004951232387ea694df4c490d12ba1/tests/signing_tests.rs) cover key/signature shapes, payload variation, normalization, domain separation and Merkle-tree shape. These are inspected test assertions, not executed results; the changed append/server/dashboard/CLI integration was outside this scope.

**Harness consequence:** Keep authority over memory writes separate from signatures on memory content. Pin an authorized genesis/key policy, distinguish unsigned from invalid records, and make replay integrity failures block protected writes until explicitly reconciled instead of treating a fallback Open mode as permission. Validate byte/count limits before allocation and benchmark total replay separately; a 1,024-key validity rule is not a preparse memory bound. Preserve historical signatures after revocation while denying new actions from revoked keys, and retain chain-head conflicts as explicit reconciliation rather than blind retry.
