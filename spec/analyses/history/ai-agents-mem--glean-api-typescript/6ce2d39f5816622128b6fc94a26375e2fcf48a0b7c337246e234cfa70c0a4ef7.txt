**OAuth administration separates spend identity but needs semantic filter validation.** Reviewed commit `261c16b61d0d7d6476c8e0ac5c81a9e4541358f9` (commit date `2026-10-22T11:02:41-07:00`). Compared with `05fc58a4563eb2322fb4628e4c630c5eaab10a84`; the complete Git comparison contains 306 changed paths.

The inspected generated OAuth-client models distinguish authentication client_id from ai_gateway.usage_client_id, an opaque case-sensitive billing/limit identity that must not be derived from client_id. They expose public/confidential client type, grant types, redirect URIs and active state. The filter contract has an actionable inconsistency: its comments restrict supported field/operator to is_active/EQUALS, while the generated operator enum accepts NOT_EQUALS and ordered comparisons and the field remains an unrestricted string. Therefore schema acceptance alone cannot establish server-supported query semantics. The generated GET mock checks bearer/accept/user-agent headers and returns an inactive static client; that fixture does not exercise revocation enforcement, tenant authorization or billing-ID mapping. TypeScript supplies Zod inbound decoding and an open client-type enum, while the outbound filter schema supplies EQUALS as a default without enforcing the documented field/operator subset.
