## Observed architecture and behavior

Spec Kit materializes development commands for different agent formats. The inspected renderer supports Markdown and TOML, with careful handling of non-string descriptions, backslashes, triple quotes, and control characters. The implementation template separates prerequisite discovery, extension hooks, checklist state, and task execution. It explicitly distinguishes requirements-quality checklist completion from implementation completion. This is useful operational structure for specification-driven work, with parts enforced by tools and parts delegated to agent instructions.

## Implications and tradeoffs for Teamagent

Teamagent should represent requirements, plans, tasks, verification evidence, and decisions as typed artifacts with stable IDs and links. Formatting commands into a host's native syntax is worthwhile, but a prompt that requests a gate does not equal a runtime-enforced gate. Extension hooks need the same provenance and permissions as other executable plugins. Checklist validity should be tied to the exact specification revision; editing a requirement can invalidate an earlier check. The inspected template's detailed workflow also illustrates why heavyweight spec processes should be selected for consequential changes, not injected into every small edit.

## Adoption decision

Offer a spec-driven coding bundle or importer rather than adopting Spec Kit's directory conventions as the entire harness architecture. Reuse format adapters and artifact templates where suitable. Enforce required state transitions in the task engine, with policy-controlled overrides recorded as decisions. Evaluate cross-platform paths, command escaping, hook failures, stale checklists, and end-to-end requirement-to-test traceability. Preserve the user's chosen workflow and allow a lightweight task path where a full specification adds little value.

## Review update — 2026-10-24

Updated focused revision: `67e0f7294e6e728ab60bf7b4590deb470448bc2d` from [github/spec-kit](https://github.com/github/spec-kit). The October 4 renderer/workflow review remains above and in its immutable maintenance snapshot. This update inspects archive integrity, integration trust and shared-file installation; it does not establish end-to-end agent correctness.

The current shared infrastructure layer verifies a declared archive SHA-256 before installation. It accepts a normalized hexadecimal digest or explicit `sha256:` prefix, rejects malformed declarations and mismatches, and uses constant-time comparison. Crucially, an absent digest remains accepted for compatibility and is logged as **unverified**; this is not a universal signed-catalog guarantee ([implementation](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/src/specify_cli/shared_infra.py#L48-L104)). Shared destination preparation rejects symlinked parents and checks resolved containment. Writes stage a temporary sibling, revalidate the destination and replace it atomically ([path handling](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/src/specify_cli/shared_infra.py#L184-L238), [writer](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/src/specify_cli/shared_infra.py#L323-L344)). These are concrete implementation safeguards; this inspection did not test races or all platform-specific filesystem behavior.

Executable integration trust is stored outside the project in user-local state. Its identity hashes the resolved project identity, integration key and package file hashes. A copied repository's mutable declarations therefore do not by themselves confer execution trust ([trust identity](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/src/specify_cli/integrations/installer.py#L326-L343)). Grant and recovery code ties ownership metadata to that trusted identity, checks recovery records and rejects expanded mutable manifests during cleanup ([grant and recovery](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/src/specify_cli/integrations/installer.py#L425-L501)). This is a stronger integration lifecycle model than treating every file listed by a repository as safe to delete or execute.

**Updated Teamagent decision:** retain the spec-workflow adapter approach, while adopting content-bound execution grants and an installation ownership ledger for future external integration packages. Require integrity status to remain explicit when a source lacks a digest. Refreshing package bytes must trigger revalidation and, where policy requires it, a fresh trust decision; cleanup authority must be limited to previously recorded ownership. Store personal execution consent separately from shared project instructions. These findings refine [skills](../skills.md), [evolution](../evolution.md) and [security](../security.md); they do not imply Teamagent's current integration registry already implements this entire package-execution model. No Spec Kit installer or agent was executed for this review.
