# OpenSandbox: self-hosted execution lifecycle

Source: [opensandbox](https://github.com/alibaba/OpenSandbox) · Category: `ai-agents-sandbox`

Review depth: **source-reviewed**. Snapshot `c7dc78a4090e5de2b9119e9bd93952cae24f87bd`; assessed 2026-10-04. This is a focused static review of the listed files, not an audit of every code path or a reproduced benchmark. No repository code, model weights, paid endpoints, or installers were run.

## Observed architecture

The Docker backend separates container operations from network management. Container setup imports CPU, memory, GPU, platform, expiry, and snapshot helpers. The network mixin handles endpoint resolution and egress sidecar lifecycle, with explicit validation of egress and credential-proxy configuration. It also accounts for Docker and Podman markers and host-loopback differences. Kubernetes and fast-sandbox implementations exist elsewhere in the snapshot, but were not audited in this focused review.

The separation is a good fit for a harness that must run the same task locally or in a cluster while retaining runtime-specific enforcement details. A common API should not erase whether a job uses ordinary containers, stronger VM isolation, or a host-process wrapper.

## Harness adoption

Shortlist as the self-hosted worker lifecycle service. The harness should pass an immutable environment image, tenant identity, workspace snapshot, resource quota, TTL, network policy, and short-lived credential references. Persist execution events and artifacts outside the disposable sandbox. Treat pool reuse, snapshots, and warm starts as performance policies subordinate to tenant separation and secret removal.

Route ordinary code builds and media rendering to isolated workers. Keep trusted lightweight text transforms on a cheaper interpreter path where its limitations are acceptable. Export actual runtime and policy version with each result so evaluations can reproduce environment-dependent failures.

## Limitations and decision

Container existence alone does not establish resistance to a hostile tenant; host configuration, mounts, kernel, runtime, and egress deployment determine the boundary. The inspected validators and sidecar plumbing are evidence of policy mechanisms, not a penetration-test result. Adoption requires fail-closed tests for unsupported policy/runtime combinations, cleanup after crashes, symlink/mount escapes, and direct egress. Compare operational burden with the hosted SDK path in [E2B](ai-agents-sandbox--e2b.md).

The [middleware fixtures](https://github.com/alibaba/OpenSandbox/blob/62a64f0b48cdd6b410f36e53c74dc7559c87719a/components/execd/pkg/web/pty_auth_test.go) cover duplicate/conflicting credentials, route/method scope, header precedence, runtime binding and no secret echo. Preserve this configuration distinction and require authenticated session ownership separately.

The [ingress proxy](https://github.com/alibaba/OpenSandbox/blob/62a64f0b48cdd6b410f36e53c74dc7559c87719a/components/ingress/pkg/proxy/http.go) removes control headers before forwarding and avoids appending an error body to an already-streaming response. Its error log includes RequestURI and raw upstream errors, so private query values still need redaction. The reverse-proxy target is derived from the request URL at this layer; upstream routing/authorization must be traced elsewhere before claiming destination safety. No sandbox, WebSocket, proxy or tests were run.

## 2026-10-28 follow-up source review

Reviewed the frozen update from `62a64f0b48cdd6b410f36e53c74dc7559c87719a` to `51bf29ce4781f7a763f3ed7ee90dc68c30f6e7e6`. This is a bounded static source review, not an upstream runtime or performance result.

In [components/egress/fastsandbox_vault_persist.go](https://github.com/alibaba/OpenSandbox/blob/51bf29ce4781f7a763f3ed7ee90dc68c30f6e7e6/components/egress/fastsandbox_vault_persist.go#L315-L406), Lazy vault inspection distinguishes unreadable/unsupported or non-v1 persisted state from a missing file. It marks that state protected and unknown instead of creating an empty replacement. Lifecycle purge refuses unknown state with 503 and recognized v2 state with 409 until lineage-aware writes exist. The code deliberately retains the legacy cleanup behavior for corrupt v1 files; this is not a blanket guarantee that all corrupt bytes survive every lifecycle path.

[Inspected fixtures](https://github.com/alibaba/OpenSandbox/blob/51bf29ce4781f7a763f3ed7ee90dc68c30f6e7e6/components/egress/fastsandbox_vault_v2_compat_test.go#L224-L304): The inspected table fixtures assert byte preservation and zero save/delete calls across active/deleted/empty/foreign/truncated v2, unknown schema and unreadable bytes during lazy access. Additional cases keep protection sticky when the file disappears or is replaced by legacy state, while allowing an initial transient I/O failure to recover. These fixtures were read, not executed; the complete vault/egress deployment was not audited.

**Teamagent implication:** Versioned memory, credential and receipt stores need distinct absent, unreadable and unsupported states. Schema downgrade or cleanup must not erase state whose lineage cannot be interpreted. Test both sticky protection after known evidence and recoverable transient failure, including terminal cleanup writers.

**Teamagent implication (inference):** Keep opaque credential references distinct from rendered secrets in typed worker messages. Bind decisions to vault revision and effective policy version; validate the exact representation before exchange and preserve secret-free diagnostics. Recheck deployment enforcement separately from successful serialization.
