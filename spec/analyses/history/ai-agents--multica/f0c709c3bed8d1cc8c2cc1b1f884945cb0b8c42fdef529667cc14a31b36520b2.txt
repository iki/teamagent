## Finding

Token-checked channel leases are a useful cloud replication pattern, with limits beyond the lease store.

## Observed design and algorithms

Acquire, renew and release use Redis Lua to atomically compare an owner token and update expiry or delete a lease. A stale release is a no-op. The readiness function verifies connectivity, loads scripts and executes a temporary acquire/renew/release cycle. The source explicitly requires startup to fail closed when readiness fails.

## Harness decision

Use channel ownership leases when multiple server replicas could process the same integration. Combine them with durable inbox deduplication, an outbox, per-conversation ordering and epoch checks at the effect boundary. This is a mechanism to study, not a requirement to add Redis to the initial single-host build.

## Limits and tradeoffs

Owner-token compare-and-delete prevents stale lease mutations; it does not by itself stop a paused former owner from sending a network message after expiry. External effects require their own stale-owner checks, idempotency strategy and reconciliation. Redis failure/failover behavior was not tested.

## Validation before adoption

Simulate a lease expiry while a process is suspended, two replicas claiming the same channel, renewal loss, failover and replayed webhook delivery. Confirm only the intended logical response reaches the conversation. No tests, live inference, installation, or production operation were performed for this review.
